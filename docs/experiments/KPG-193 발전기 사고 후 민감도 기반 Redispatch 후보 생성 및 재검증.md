# KPG-193 발전기 사고 후 민감도 기반 Redispatch 후보 생성 및 재검증

# \[KPG-193 발전기 사고 후 민감도 기반 Redispatch 후보 생성 및 재검증\] — 2026-09-30

## 가설

발전기 N-1 사고로 선로 과부하가 발생한 경우, 사고 후 계통 상태에서 발전기 출력 변화에 대한 선로 조류 민감도를 계산하면 과부하를 완화할 가능성이 높은 Redispatch 후보를 우선 선별할 수 있을 것이다.

다만 민감도는 국소 선형 영향도이므로, 민감도만으로 제어 효과를 확정하지 않고 실제 Redispatch를 적용한 뒤 AC Load Flow 및 Security Analysis로 재검증해야 한다.

## 설정

- 데이터셋/버전: KPG-193 v2.0 (`KPG193_ver2_0_powsybl_full.mat`)
- 해석 도구: PyPowSyBl 1.16.1
- 사고 대상: `GEN-124#1` 발전기 탈락
- Load Flow balancing: Distributed slack
- Balance type: `PROPORTIONAL_TO_GENERATION_P_MAX`
- Security Analysis: PyPowSyBl AC Security Analysis
- 사고 후 주요 위반 설비: `LINE-134-193`
- 설비 한계: RateC = 2172 MVA
- 민감도 대상: 사고 후 생존 발전기의 출력 변화가 `LINE-134-193` 유효전력 조류에 미치는 영향
- Redispatch 방식: 발전기 1대 +10 MW / 발전기 1대 -10 MW의 balanced Redispatch
- 후보 수: 상위 3개
- 후보 선정 방식: 민감도 기반 예상 조류 절댓값 감소량 순위 + 동일 Bus pair 중복 제거
- 최종 검증: AC Load Flow + 전체 계통 Security Analysis
- 테스트 상태: 전체 pytest 59개 통과

## 분석

민감도 기반으로 선정한 상위 후보들이 실제 AC Load Flow 재검증에서도 모두 `LINE-134-193`의 과부하를 완화하는 방향으로 동작했다.

특히 민감도 순위 1~3위와 실제 AC 검증 순위도 동일하게 나타났다. 따라서 이번 사례에서는 사고 후 민감도가 Redispatch 후보의 우선순위를 정하는 데 유효하게 활용될 가능성을 확인했다.

다만 민감도 예측값은 **선로 유효전력 조류 변화량(MW)**이고, 실제 AC 검증에서 확인한 개선량은 **피상전력(MVA)**이므로 두 수치를 동일한 물리량으로 직접 비교해서는 안 된다. 이번 실험의 의미는 두 값의 수치 일치 여부가 아니라, 민감도로 선별한 제어 방향이 실제 AC 해석에서도 과부하를 완화하는 방향으로 확인되었다는 점이다.

또한 최선 후보인 `GEN-106 +10 MW / GEN-193 -10 MW`를 적용해도 부하율은 105.60%에서 105.35%로 감소하는 데 그쳤으며, 과부하는 완전히 해소되지 않았다. 따라서 **민감도가 높은 발전기라고 해서 해당 제어가 최적 Redispatch이거나 위반을 반드시 해소하는 것은 아니다.**

전체 계통 Security Analysis를 다시 수행한 결과 Redispatch로 인한 신규 위반은 발생하지 않았으나, 기존 `LINE-134-193` 위반은 남아 있었다.

초기 후보 생성에서는 `GEN-193`, `GEN-193#0`, `GEN-193#1` 등 동일 Bus에 위치하고 민감도가 같은 발전기들이 상위 후보를 반복적으로 차지하는 문제가 있었다. 이 경우 실제 AC 검증 결과도 거의 동일해 후보 비교의 의미가 작았다.

이를 개선하기 위해 동일한 Up Bus / Down Bus 조합을 중복 후보로 간주하여 대표 후보만 남기는 방식을 추가했다. 이후 `GEN-106`, `GEN-100#2`, `GEN-53#10` 등 서로 다른 Bus의 발전기가 후보에 포함되어 실제 제어 대안을 비교할 수 있었다.

이번 실험은 다음 흐름을 실제 계산으로 확인했다.

```
Generator N-1 사고
→ Security Analysis
→ 주요 과부하 선로 선택
→ 사고 후 Sensitivity Analysis
→ Redispatch 후보 생성
→ AC Load Flow 재계산
→ 전체 계통 Security Analysis 재검증
```

이 결과는 향후 AI EMS에서 민감도 기반 후보 탐색 기능을 활용하더라도, 최종 계통 상태와 제어 효과는 실제 물리해석으로 재검증하는 구조가 필요함을 보여준다.

### AI EMS 활용 가능성

이번 실험에서 구현한 흐름은 발전기 사고 이후 계통 상태를 확인하고, 과부하 선로에 영향을 크게 주는 발전기를 찾아 Redispatch 후보를 만든 뒤 실제 계통해석으로 효과를 다시 확인하는 과정이다.

이 과정에서 작성한 Security Analysis, Sensitivity Analysis, Redispatch 후보 생성, AC Load Flow 및 Security 재검증 함수들은 각각 독립적으로 사용할 수도 있지만, 연속된 분석 절차로 조합할 수도 있다.

예를 들어 AI EMS에서 발전기 사고나 과부하가 감지되었을 때 다음과 같은 분석 흐름에 활용할 수 있다.

```
발전기 사고 또는 위험 상태 확인
→ Security Analysis로 위반 설비 확인
→ Sensitivity Analysis로 영향이 큰 발전기 탐색
→ Redispatch 후보 생성
→ 실제 계통해석으로 후보별 효과 검증
→ 개선 정도와 잔존 위반 비교
```

이번 실험에서는 `GEN-124#1` 탈락 이후 `LINE-134-193` 과부하에 대해 여러 Redispatch 후보를 생성하고 실제 AC 해석 결과를 비교했다. 이처럼 민감도 결과를 이용하면 모든 발전기 조합을 동일하게 검토하기보다, **문제 선로에 영향이 큰 후보를 먼저 좁혀 후속 계산 대상을 줄이는 용도**로 활용할 수 있다.

또한 `GEN-106 +10 MW / GEN-193 -10 MW` 후보는 실제 해석에서도 과부하를 완화했지만 위반을 완전히 해소하지는 못했다. 이 결과는 향후 AI EMS에서 제어 후보를 추천할 때 단순히 “효과가 있을 것으로 예상되는 후보”를 제시하는 데서 끝내지 않고, **실제 계통 상태에 적용했을 때 얼마나 개선되는지와 추가 위반이 발생하는지를 함께 확인하는 절차**가 필요함을 보여준다.

이번에 작성한 기능들은 향후 Agent 또는 운영 지원 기능과 연결할 수도 있다. 예를 들어 사용자가 “이 사고 이후 어떤 발전기를 조정하는 것이 좋을까?”라고 요청하면, Agent가 직접 계통 결과를 생성하는 대신 현재 구현한 분석 함수를 순차적으로 호출하고, 계산된 후보와 검증 결과를 정리해 제공하는 방식이다.

현재 구현은 10 MW 단위의 balanced Redispatch 후보를 비교하는 단순한 형태이므로 실제 EMS의 제어 로직이나 OPF/SCED를 그대로 대체하지는 않는다. 다만 **위반 확인 → 영향도 분석 → 후보 생성 → 물리해석 재검증**이라는 분석 흐름 자체는 향후 AI EMS에서 제어 추천, 운영자 지원, Tool orchestration 등의 기능을 구성할 때 활용할 수 있는 기본 단위로 볼 수 있다.
